## بدء الاستخدام

ثبّت الإصدار 0.4.1 أو الأحدث على كل جهاز مرة واحدة. أغلق النسخة القديمة بعد حفظ العمل. سجّل بنفس الحساب؛ بيانات الشركة تُحمّل من الإنترنت، ولا يلزم وجود الأجهزة داخل الشركة أو على الشبكة نفسها. تم نقل 72 موظفًا وكشف شهر واحد و3 حسابات يوم 29 سبتمبر 2026. قاعدة الجهاز الأصلية ونسخة قبل النقل محفوظتان في مجلد بيانات التطبيق.

لا تستمر في إدخال بيانات على النسخة المحلية القديمة: تعديلاتها لا تصل إلى السحابة. أي جهاز آخر يحتوي بيانات محلية مختلفة يجب مراجعتها واستيرادها قبل الاستغناء عنها؛ لا يتم دمج قواعد قديمة كاملة تلقائيًا.

الدخول الجديد يحتاج إنترنت. بعد الدخول يمكن تسجيل التعديلات المعتادة عند انقطاع الاتصال؛ تُحفظ في قائمة انتظار دائمة وترسل عند عودة الاتصال. اعتماد الشهر، صرفه، الاستعادة وإعادة الضبط وبعض العمليات الجماعية تحتاج اتصالًا. عند اختلاف تعديلين للسجل نفسه، يتوقف التعديل المتعارض للمراجعة بدل الكتابة فوق عمل الآخر. قبل التخلص من التعديل المحلي تُحفظ نسخة احتياطية.

السوبر أدمن يستطيع إخفاء الحسابات. الأدمن العادي لا يرى الحساب المخفي ولا يستطيع تعديل صلاحية السوبر أدمن. هذه الحماية مطبقة في الخدمة كذلك. إخفاء حساب لا يخفي بيانات الموظفين التي أدخلها؛ بيانات الشركة مشتركة.

## نشر تعديل جديد من جهاز صاحب المشروع

تعديل ملفات الكود أو رفعها إلى GitHub وحده لا يحدث أجهزة المستخدمين. يجب بناء ونشر إصدار برقم أعلى. بعد تسجيل الدخول في Supabase CLI وGit Credential Manager:

```powershell
```

الأمر يشغّل الاختبارات، يبني التطبيق وخدمة المزامنة، ينشر الخدمة، يرفع نسخة Windows إلى مسودة GitHub Release، ويتحقق من وجود المثبّت وملف `latest.yml` قبل نشر الإصدار وإشعار الأجهزة. لا تُضمّن مفاتيح الإدارة في التطبيق. `cloud.public.json` يحتوي معلومات اتصال عامة فقط.

الرفع يتم بالتتابع إلى مسودة واحدة وتُقارن بصمات الملفات قبل النشر. إذا انقطع الرفع بعد البناء، أعد نفس الأمر مع `--resume` لاستكمال الإصدار غير المنشور من ملفات `release` الموجودة؛ لا تستخدمه بعد تعديل كود التطبيق دون إعادة البناء.

عند تغيير مخطط قاعدة البيانات، راجع وطبّق الترحيل الجديد المتوافق مع النسخ الحالية قبل النشر. الترحيلات الثلاثة حتى `202609290002_cloud_restore.sql` طُبقت على المشروع عبر SQL؛ لا تعاود تشغيل الترحيل الأول. سكربت الإصدار ينشر الدالة فقط ولا يشغّل ترحيلات قاعدة البيانات تلقائيًا. لا تستخدم تغييرًا يكسر توافق الأجهزة التي لم تتحدث بعد.

يحاول التطبيق فحص الإصدار بعد فتحه، وعند رجوع الاتصال أو استيقاظ الجهاز، وبعد إشعار الإصدار، وكل خمس دقائق كاحتياط. يُنزّل التحديث تلقائيًا. التثبيت ينتظر لوحة البداية وعدم وجود تحرير أو طلب نشط أو عمليات مزامنة معلقة، ثم يعيد تشغيل التطبيق. الجهاز المغلق لن يتحدث حتى يُشغّل التطبيق ويتصل. لا يمكن ضمان وصول فوري إذا كانت الخدمة أو شبكة الجهاز غير متاحة.

## النسخ والحماية والتكلفة

توجد نسخ محلية، ونسخة سحابية قبل الاستعادة وإعادة الضبط، ونسخ سحابية دورية عند تغيّر البيانات مع الاحتفاظ بآخر سبع نسخ. الاستعادة متاحة للأدمن وتستبدل بيانات الشركة لجميع الأجهزة بعد التأكيد، مع الاحتفاظ بالحسابات الحالية. السجلات التي لم تتزامن على أجهزة أخرى قد تحتاج مراجعة بعد الاستعادة.

مفاتيح الخدمة وبيانات نشر GitHub تبقى في أدوات صاحب المشروع. جلسة التطبيق مشفرة على الجهاز. هذا لا يغني عن حماية حساب Windows ونسخ البيانات المحلية.

الحل يستخدم الخدمات المجانية ولا يحتاج سيرفر محلي، لكنه يخضع لحدود وتوفر الخطط المجانية. راقب استهلاك المشروع من لوحة Supabase. يتم تنزيل صورة بيانات الشركة عند تغير إصدارها؛ مع تضخم البيانات أو عدد الأجهزة قد يلزم الانتقال إلى مزامنة تفصيلية لتقليل النقل. إيصالات العمليات محفوظة لمنع التكرار وتحتاج متابعة حجمها بمرور الوقت.

كان هناك رمز GitHub قديم مضمن في نظام التحكم السابق وتم حذفه من المصدر الجديد. يجب إلغاؤه من إعدادات GitHub إذا لم يُلغَ بالفعل، لأن نسخه القديمة قد تكون موزعة على أجهزة المستخدمين.
